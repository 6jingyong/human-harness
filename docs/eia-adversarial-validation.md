# EIA A→B→C 对抗性功能验证（2026-11-09）

## 测试目标

不再用来源 SHA 或字段格式充当“模型可靠性”的指标。故意注入逻辑荒谬但看似符合 API 的输出，实际运行 Human Harness 的执行器、审阅与下游任务，检查污染能否传播、拒绝重做能否恢复。

当前测试文件：`tests/eia-adversarial-pipeline.test.ts`。这是**受控的恶意 Agent fixture**，不是外部 Codex/Skill 的真实模型测试；固定测试文本不等于真实环境分析结论。

## 三种对抗场景及发现

| 场景 | 攻击 | 实测应达到的结果 | 已发现的边界 |
| --- | --- | --- | --- |
| A 胡乱提取 | A1 返回合法 JSON，但字段是菜谱、土豆与巧克力，包含 `UNRELATED_A_PAYLOAD`，却声称两个模板检查均通过，并引用本轮合法证据 ID。 | A1 只能进入 `review`；B1 保持 `blocked`；未审核的 A 不允许下载。 | **无法自动识别菜谱与环评无关**。单靠合法 JSON、检查 ID、证据 ID 和自检通过不代表内容正确。 |
| A、B 连续造假，人工退回 | 人工发现 A 菜谱，退回并要求重新抽取；A 重做后才批准。B 随后谎称“月球引力使污染自动消失”，也标记自检通过。人工再次退回，要求依据 A 的事实重做。 | A/B 重做时能收到历史反馈；B 仅收到新批准的 A，C 仅收到新批准的 B 与另一分支 B2，旧错误候选不会作为有效输入；最终报告不包含两个攻击标记。 | 能防止**未批准**错误继续传播，不等于自动识别谬论。 |
| 人类连续误批准 | 操作员故意批准 A 的菜谱 JSON，继而批准 B 的无依据结论，并完成 Human 决定。 | C **实际收到**被错误批准的 B 结论，并生成受污染的候选文档；由于 C 自身仍为 `review`，未最终批准前不能下载。 | **严重剩余风险：如果连 C 的最终审核也误批准，错误结论便会正式交付**。目前没有独立的内容正确性验证器。 |

## 需要区别的保障范围

- 结构/权限校验：数据格式、模板检查项数量/ID、授权来源引用、任务依赖、人工审核闸门。**当前机制可验证**。
- 内容正确性：字段与原件是否对应、因果推论是否合理、数字是否被捏造或结论是否超出已给资料。**当前机制不能独立验证**；`methodChecks.status=passed` 是 Agent 自述，不是专业认证。
- 误批准风险：人工确认是授权依据，不保证事实永真。这是现阶段有意暴露而非假装已修复的局限。

## 下一轮应怎样改善而非堆砌规则

1. 在项目模板里为 A/B 设计**专门的独立验证步骤**：A 的结果对照对应原件摘录；B 的每项结论必须能映射到上游 A 的事实 ID；C 仅做确定性成果排版。
2. 先通过真实 Skill/模型执行以上验证，在测试中注入菜谱、无依据污染合格结论、伪造来源与混淆单位，再统计**发现率、误放行率、误退回率**。现有测试只是给出安全边界，不能推出任何模型准确率。
3. 必须能退回并重新执行原 WorkItem，确保真正错误候选保留历史但不会被下游当作当前结果。
4. 不要把 AI 自己写的“检查已通过”当作独立校验；独立验证的输入、执行器和结果应明确留痕。

**项目模板已将 A/B/C 分为三个角色。对同一份资料，A→B→C 必须顺序；多个资料分支可以流水线并行。**
