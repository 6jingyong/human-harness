# Human Harness · 执行时补充信息的 Human Todo 闭环

## 设计边界

Human Harness **不承担通用文件语义提取引擎**。字段、来源、提取规则、验证条件和所需 Skill/Plugin 应主要由项目模板声明，并由当前 Agent 工具链执行。核心只保存项目状态、授权范围、来源、候选产物、版本及审核/交接记录。

目前最重要的补全：模板定义得再好，实际执行时也可能缺少信息；Agent 可以将问题交给 Human Todo，再根据人类回复继续执行。

## 已实现的最小闭环

1. Agent 本次输出可选择 `materialRequests: [{materialId, reason}]`；不能凭空创建新的模板资料类型，必须引用当前项目模板声明的 `materialId`。
2. 运行器检查请求是否重复、是否超过限制（一次最多 5 项，同一任务同一材料只能请求一次），以及请求是否属于当前模板。未通过会让本次任务失败，不会改变项目资料。
3. 如果有请求，这次 Agent **不提交已完成候选成果**，而是进入 `waiting_input`，运行结果记录为 `needs_input`，同时在左侧 Human TodoList 建立对应的待办。右侧 Agent TodoList 显示“等待人工答复”。
4. 用户直接从左侧待办提交书面说明。可以明确写“暂时无法提供”。这份答复是人工说明，不会自动改变原始文件的“已核验”状态。
5. 若同一轮有多个问题，须全部答复，原 Agent 才恢复 `ready`；原后台调度器随后自动重新执行。Agent 的受控输入中包含此前的问题和答复。
6. 相同材料的重复补问会被拒绝，避免重复执行形成无限询问循环。所有问题、回答、运行身份和时间都保存在项目 SQLite 状态/事件中。

## 没做的事

- 不自动创建任意 Human/Agent 步骤；动态问答只是基于模板已有材料的有界补充说明。
- 不直接将人类的回答视为已核实的原始文件，也不把回答添加到原件库或改变文件版本。
- 暂未通过该 Human Todo 接收新的附件；需要真实新文件时仍须遵循原材料提交及人工验收流程。这个扩展应与模板的材料生命周期结合，避免绕过已有验证。
- 不对“无法提供”的回答编造事实；模型应按不确定性处理。
- 浏览器端 Demo 验证与受控执行器测试均不是对真实 Codex 模型的能力验收。

## 验收

- `tests/human-request-handoff.test.ts`：暂停、实际生成 Human Todo、人类回答、重新执行收到前次问答、正常审核完成。
- 越权请求、重复补问、空答复和假造新原件被拒绝。
- `tests/task-workbench.test.ts`：请求出现在左栏、对应 Agent 在右栏等待。
- 原有 Chromium Demo 全流程保持不回退。

## 下一步

使材料模板方法与补料请求建立显式绑定：用户补充文本或附件之后，按模板的方法验证，再有选择地解除具体任务的阻塞。优先实现真实补充资料的原件版本管理与失效传播，避免一个新文件让整份旧报告仍被当作最新依据。
