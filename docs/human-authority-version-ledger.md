# Human Harness · 人类最终决定权与可追溯版本账本

> 2026-11-09 设计决策。此文件是后续实现与验收的约束，不宣称本提案所有能力已经完成。
> 本项目不 fork 或复刻 Git；只采用不可静默覆写、显式当前版本、来源链、回退新提交和影响传播的思想。

## 一句话原则

**人类对项目当前采用的成果具有最高决定权；任何 Agent 或脚本不得私自推翻这一决定；但无论人类还是 Agent，均不能静默改写已经发生的历史。**

- **最高权力是决定权，不是自动真实性认证。** 用户可批准错误/未核实内容并继续，这属于「用户确认采用的前提」，不等于系统独立验证其准确。
- **当前采用版本可变，历史只追加。** 用户修改、接受例外、撤销或恢复旧结论，均产生新的变更记录；旧版及当时的上下游依据仍可查。
- **事实/成果分层。** 模板约束和格式合法性由可信 Runtime 检查；专业真实性由既定方法、Agent 自检与人类复核决定，不能让模型的自证变成权限。
- **每个 Agent 仅看到获授权的当前上游成果。** 不因版本修正而使 B/C 自动越权读取 A 的原始材料。
- **并行项目局部重算。** 修改一个被引用的上游成果，不自动让无关分支失效。

## 对应 Git 的最小概念

| Git | Human Harness |
| --- | --- |
| repository | project（含模板固定快照、项目原件、任务图） |
| commit | 一次经过 Runtime 入账的成果或人工决策 |
| HEAD | 当前明确采用的已批准成果引用，而非「数组最后一项天然有效」 |
| parent / history | 原结果引用、前后版本、变更原因 |
| diff | 内容差异和任务状态变化；原始内容仍完整保存 |
| revert | **新提交**恢复旧内容或旧决定，不删除从前的提交 |
| branch | 可并行推进的任务依赖分支，不必立即模拟 Git 的可变分支树 |
| merge | 人工确认多个输入后，生成汇合成果；保留所消费的上游 artifact IDs |

**不是**要引入完整 Git 命令、Git hooks 或所有分支合并语义。

## 需要固化的数据合同（设计目标）

### Artifact revision

- 稳定的 `artifactId`、`ownerStepId`、`revision`、`content` / `contentHash`、`createdAt`。
- `createdBy: { kind: 'agent' | 'human' | 'script', id?: string }`：当前本地单用户版可只确定执行者类别，不能伪造真实用户名。
- `basedOnArtifactId`：人工修正的父版本；不原地覆写旧 `content`。
- `inputArtifactIds[]`：生成本版本时实际消费的已批准上游产物，不能只依赖模板静态 DAG 推断。
- `review: { decision, actor, reason, timestamp }` 与 `approvalStatus`：明确区分「被生成」「被确认采用」。
- `approvedArtifactId`：每个输出步骤指向当前有效的已确认版本（HEAD）。候选和历史都不能冒充 HEAD。

### Audit / decision event

每次用户操作保留事件 ID、项目 ID、动作类别、执行者类别、时间、目标步骤、操作前/后引用、原因、影响步骤 ID、并发保护时的 expected HEAD。必要时附结构化差异摘要；不要求在事件表重复存一份大型文档。

- `human.approved`：接受候选。
- `human.amended`：内容修正并接受，产生新版本，记录 parent。
- `human.overrode_check`：未通过/未验证的专业检查由人类附理由允许采用。
- `human.reverted`：复制旧内容为一个**新的**当前版本，保留中间修改历史。
- `work.invalidated`：下游因依赖版本变更失效，保留失效前成果供查阅。

现有 `project.events` 和 SQLite `event_log` 可演进，不建一套和双 Todo 竞争的「审批中心」。当前 SQLite 记录是应用层持久化日志，**不是具备篡改检测的密码学不可更改日志**，文案不得混淆。

## 状态迁移及优先级

1. Agent 提交候选后进入 `review`；**Agent 不能自己把候选变成 HEAD**。
2. 人类在 Human Todo 可以：批准、退回、直接编辑后批准；对未通过的检查保留书面理由。执行器无条件服从已登记的当前采用结果，而不是自行重新论证。
3. 人类对 `done` 的输出也可提出新版修正：先展示**影响预览**，再用 expected HEAD 原子提交。若 HEAD 已变化，返回冲突并要求重新查看，避免覆盖别人的较新决定。
4. 已修正的上游 HEAD 推进后，将所有依赖它的下游（含 `dependsOn`、`when`/工作完成条件、必要时条件触发材料）标记为 `stale/needs_regeneration`。保留其旧产物，只禁止将其继续当成当前有效交付。独立并行分支不动。
5. 活跃中的受影响 Agent **不能默默被撤销，也不能继续提交到已变更的旧 HEAD**。必须显式取消/等待，或在提交时由 Runtime 比较上游快照而拒绝陈旧候选。
6. 复用既有 Human/Agent 双 Todo，把「查看影响、确认覆盖、重新执行」显示在正常任务详情，不新增整页独立审批体系。
7. 回退不是旧版本从未发生，而是一个新的采用决定。旧结果、错误结果与被否决意见都可以追溯。

### 示例：A → B → C

- A v1（Agent 误提取 `380`）→ Human 改为 A v2（`220`）并批准。
- B v1 只读 A v2，C v1 只读已审 B v1。
- Human 后来把 A v2 改为 A v3（`230`），记录 `A:v2 → A:v3` 和理由。
- B v1、C v1 保留历史，但不能作为当前有效成果下载；B 等待基于 A v3 重跑，随后 C 只依赖新 B。独立任务 D 不受影响。
- 若 Human 要恢复 A v2，创建 A v4（内容复制自 v2），记录回退原因，不能直接删除 A v3。
- 即使 Human 明确批准毫无根据的 `999`，系统也不得自行把它恢复为 `220`；只能在检查收据中提示不确定性，同时尊重人工决定。

## 迭代顺序与验收

### 已存在的基础

- 项目/模板快照、双 Todo、项目级并行、提交人工补件和审核。
- 原件替换已经有有限的影响传播与历史失效机制。
- PR #5：仅对**审核中的** Agent 候选允许人工另存修订稿并批准；暂不支持已完成成果事后覆盖。

### 下一批应实现，不依赖 Codex 额度

1. 当前版本显式 HEAD + 版本来源与人工 actor/rationale。
2. 已批准成果的人类新修订，先预览影响再原子提交。
3. 上游修订时的逐级失效、独立分支保持、旧产物只读历史。
4. 以当前 HEAD 为唯一授权输入，记录运行输入快照，阻止旧输入竞争提交。
5. 任务详情展示版本链、改动原因、影响与恢复入口；流程状态仍属原双 Todo。
6. 后续才考虑数据库恢复、强审计、多人权限与授权签名，先不重复 Codex 的 Skill/Plugin/MCP/通用文件解析。

### 必须通过的回归用例

- A 经人工修订后 B 只能看到人工版，不能看到旧 A；B 不能自动回读 A 原件。
- A/B/C 全部完成后，人改 A；B/C 旧结果成为历史，D 独立分支仍有效。
- 两个人工编辑基于同一旧 HEAD 并发提交：第二个必须冲突，不能静默覆盖。
- 有运行中下游任务时改上游：显式提示取消/稍后再改，或拒绝陈旧提交；不允许静默接受旧输入成果。
- 回退产生新 revision 和事件，不删除任何中间修订。
- Agent 不可篡改自己的审核状态、已审核成果指针、人工解释或历史事件。
- 正确记录人类「批准有意错误结果」；代理 A→B→C 故意污染试验仅在真实 Codex 额度恢复时执行（Issue #4），模拟测试不得冒充真实模型验收。
