# Human Harness — Codex 版开发路线与交付验收

> **决定日期：2026-11-08。** 本文定义 Codex Edition 的开发顺序与完成标准，**不是已完成功能清单**。当前仓库的实际可运行底座仍是 Mastra/demo，Codex app-server 和原生 Plugins 尚未接入。本文沿用现有 `hh.package/1`、`hh.task/1`、`hh.result/1` 协议，不新造一套项目状态机。
>
> 产品入口：[中文说明](README.zh-CN.md) · [English README](../README.md) · [Codex 原生插件策略](codex-native-plugins.md) · [模板素材方法](template-material-processing.md) · [上游 Codex app-server](https://developers.openai.com/codex/app-server)

## 1. 一句话目标

**用户选择手工编写的项目模板 → 按一个 Human TodoList 提供真实资料和决策 → Codex 使用当前环境已安装的 Skill/Plugin/MCP 执行被授权的 Agent 任务 → 返回可追溯候选结果 → 根据模板完成检查、推进项目或生成具体待办 → 交付已确认的成果。**

我们只做**项目层**。不开发第二套 Agent Loop，不造插件市场，不重复编写通用 PDF/DOCX 解析器，不依赖 Codex Cloud、托管任务和远程协作等联机产品功能。

使用外部模型/API、在线文件或地图工具时仍可能联网。“不依赖 Codex 云服务”不等于强制完全离线。

## 并行默认原则（2026-11-08 修订）

**Human Harness 是 Parallel-first：人类任务与 Agent 任务按模板依赖图并行推进，而不是由一条主 Agent 会话串行驱动。** 单个 WorkItem 内是否再使用 Codex 的 Subagents 属于另一层优化，不等同项目级并行。参见 [并行架构与验收](parallel-first.md)。

当前项目状态与数据库事务已支持两个互不依赖的任务同时运行，已补回归测试；但**现有工作台仍以全局 `busy` 锁阻止并行交互，`run_agent` 仍阻塞至模型调用结束**。因此这只能算后端基础，不得宣称 V1 并行工作台已完成。

将 **P1.1“单个 Codex 任务真实执行”** 与 **P1.2“多个 Codex 工作项并行+Human Todo 不阻塞”** 区分验收。P2 原生插件接入应在 P1.2 后展开。

## 2. V1 交付边界：什么才叫“Codex 版完成”

完成不是“Codex 进程能启动”，而是以下全部条件能在本地从头演示：

- [ ] **项目可启动**：用户可以创建/导入一个符合协议的模板，建立项目实例，看到两个角色视图（Human TodoList 和 Agent 工作队列）。
- [ ] **Codex 真执行**：至少一项真实 Agent WorkItem 使用本机 Codex app-server 执行；具有真实事件、输出、失败及中断状态，不使用演示文本充当真实模型结果。
- [ ] **插件真调用**：查询本机已安装 Skill/Plugin/MCP 的有效状态，在实际任务中成功调用至少一个既有能力，并保留调用证据；不可用时准确说明缺什么，不伪造读取成功。
- [ ] **素材方法有效**：模板可以规定输入、需要提取的字段、验证目标及异常去向；可读材料实际生成有来源的候选信息，或清楚返回不可解析/待用户补料。
- [ ] **一个 Human TodoList**：提交材料、解决缺项/冲突、检查候选成果、专业决策等都属于普通用户任务；**不另造审批模块**。
- [ ] **阶段真正推进**：完成一个至少包含“资料 → AI → 用户处理 → AI/交付”的端到端项目流程；已存在的土地污染调查分支演示仍需保持条件正确，特别是未完成机构工作前不能提前索取检测/质控报告。
- [ ] **可交付且可追溯**：至少支持经核验的 Markdown/JSON 成果与原始来源记录；PDF/DOCX 只有在真实安装的工具确实能读取或生成时才在 UI 标记为可用，不宣称内建专业排版。
- [ ] **普通用户可部署**：本地安装说明、Codex CLI 检测、登录/模型状态提示、错误提示、数据备份说明与自动回归测试完整；**仅定位为单机可信环境**，不冒充已具备公网部署安全性。
- [ ] **执行器不重复维护**：正式 Codex 版以 Codex 为唯一默认 Agent 执行器；Mastra 原型完成迁移验证后删除或迁出主产品，不长期保留双底座。

**V1 不包含**：中国版 Octop 适配、完整 EIA 行业 Skill 集、真实 GIS 自动调查、监管签发、多用户/多租户、公开部署、云任务同步、插件商店、自研通用 PDF/DOCX/OCR 引擎。后续行业能力应复用生态，不阻碍通用 V1 发布。

## 3. 六阶段开发顺序（有完成门槛，不并行扩张）

### P0 — 锁定边界与工程基线

**实施记录（2026-11-08）**：已提交 P0 最小可替换执行器接口。新增 `src/executors/contracts.ts`（限定输入、结构化候选输出），`src/executors/runner.ts`（唯一负责任务预约、合法证据选择、结果校验/入账、失败状态），`src/executors/demo.ts`（明确标注模拟）并将 `src/executors/mastra.ts` 收敛为无项目状态写权限的适配器。项目 API 与既有流程测试已改用 runner。新增测试覆盖：执行器只能见到授权证据、不能取得内部上传路径或整个项目状态；越权输出被拒绝；配置 `HH_EXECUTOR=codex` 在真正接入前**显式失败而非退回 demo**。

**验收范围说明**：本阶段的接口仅实现当前必要的 `execute`，Codex 特有的运行事件、中断与恢复、能力发现属于 **P1/P2**，需依据实际 app-server 协议补充，避免提前发明与上游不一致的 API。当前不宣称完成真实 Codex 模型调用。



**目的：避免进入 Codex 接入阶段后同时修改协议和整套 UI。**

开发：
- 将当前 Protocol 1.0 和现有测试作为固定基线，保留现有项目模板、SQLite、Human Todo 和状态事件逻辑。
- 新增一个薄的 `ExecutorAdapter` 接口，只表达“启动/输出事件/成功失败/中断/恢复/查询能力”；不要先扩充为通用多 Agent 框架。
- 说明任务输入边界、原件访问方式、候选结果与业务状态变更的隔离；Codex 没有权力直接改写项目数据库。
- 原型 Mastra 适配器保留至 P1–P4 验证通过，但**不继续为它添加新功能**。
- 固定“主分支稳定基线 + 小阶段 PR”的协作方式；先处理当前基础 PR 的代码审查与合并，再开展大型运行时迁移。

**验收**：现有 `npm run typecheck`、`npm test`、`npm run build` 通过；有最小适配器契约与边界测试；旧演示项目不回退。

### P1 — 真正跑通本地 Codex（第一优先级）

**目的：让 Human Harness 工作台执行一项真实 Codex 任务。**

开发：
- 从**后端**管理 `codex app-server` 子进程，以本地 stdio / JSON-RPC 通信；不从浏览器直连未授权的 Codex 端口。
- 使用已安装 Codex 的协议导出或固定版本 schema；完成初始化、登录/模型可用性检测、`thread/start`、`turn/start`、事件订阅、结束与异常路径。
- 将既有 `hh.task/1` 转成 Codex 输入，将真实结果回写成经过 `hh.result/1` 校验的候选结果；由项目运行时决定下一步。
- 持久保存 `projectId, stepId, runId, threadId, turnId` 关联；处理重复事件、超时/断线与中断，不允许过期结果覆盖新任务。
- 从一个**不依赖插件、只使用无敏感输入的任务**开始，实测真实模型返回。无可用凭证时只能通过协议层测试，不得称真实运行通过。

**验收**：在同一项目中可点击“运行” → 收到真实 Codex 事件 → 保存候选产物 → 由 Human TodoList 处理结果；失败和取消后状态正确，重启不会误判已成功。CI 用模拟 RPC 录制事件验证；实际模型调用作为独立手动验收，不在公开 CI 中写入凭证。

**不做**：自研 Agent Loop、上下文压缩、浏览器远程交互、Codex Cloud。

### P2 — 原生 Skill / Plugin / MCP 生态（第二优先级）

**目的：让 Codex 直接使用用户已有的能力。**

开发：
- 读取 Codex `skills/list`、`plugin/list` / `plugin/installed` 和 MCP 服务可用状态；展示“已安装/启用/缺连接/不可用”。
- 模板只声明**业务能力需求与首选绑定**，在当前机器解析到真正存在的 Skill/Plugin/MCP；不在模板内保存本机绝对路径或凭证。
- 把选定 Skill 与任务输入传给 Codex；**使用真实工具调用事件证明插件被调用**，而不是从输出中的“我使用了插件”来判断。
- 当前插件缺失时显示可理解的原因和原生安装/授权指引；不做静默安装，不自建插件市场。
- **安全限制**：上游 `disabledPluginIds` 目前不能作为真实能力过滤手段；每项任务的材料范围和工具权限必须由实际运行环境约束。

**验收**：真实安装一个现成、只读的工具/Skill → Human Harness 能发现它 → 给它一项任务 → 保存真实结果和调用记录；禁用/卸载/未授权时能正确阻塞并指向用户操作，而不是伪造成功。

**不做**：开发自己的 PDF、DOCX、OCR、GIS 工具作为前置条件。

### P3 — 模板升级为“工作方法定义”

**目的：让 Agent 不是随意读材料，而是按项目类型执行规则。**

开发：
- 在当前 `hh.package/1` 上**小范围扩展正式 schema**（无旧实验兼容负担），声明：材料识别目标、需要提取的字段、验证方法/来源要求、跨材料依赖、异常处理方式、所需 Skill/Plugin 能力。
- 明确**模板只写业务方法，不复制现成插件的实现说明**。例如定义“检测报告必须抽取样品编号/点位/结果/单位并引用来源”，而不是嵌入 PDF parser 代码。
- Agent 负责从当前有权限的 Skill/插件中执行识别提取；确定性规则先处理简单一致性检查；专业不确定性和无法解决的冲突生成**具体 Human WorkItem**。
- 既有用户“资料已收到”≠“解析已成功”≠“检查已通过”；处理输出均有源材料 ID/版本，避免错误引用。
- 避免把用户尚未产生、尚未到请求时机的材料当成错误；等所需依赖材料就绪后再做跨文件检查。

**验收**：使用 P2 已运行的现成文档工具，处理一份有合适测试许可的材料；模板指定输出字段；能给出来源或者明确表示不可定位；缺失字段/材料冲突能触发**具体且不重复**的用户 Todo，不创建另一套审批界面。

**不做**：追求支持所有 PDF 排版格式，或者为一个行业提前写完整判断专家系统。

### P4 — 从“局部功能”变成“完整项目”

**目的：验证真正的产品闭环。**

验收场景 A（通用最小项目）：
1. 新建“资料整理 → 形成简要成果”模板与项目。
2. 用户提供文本或可由已安装插件读取的文档。
3. Codex 根据模板提取指定信息，输出候选事实和出处。
4. 发现故意设置的缺项时生成一条具体用户 Todo；用户解决后继续。
5. 最终输出经项目要求审阅的 Markdown/JSON 成果，保留来源和任务事件。

验收场景 B（土地污染调查模板的**软件流程回归**）：
1. 第一阶段可正常退出，不激活采样报告任务。
2. 采样分支必须先完成人类专业决策和实际机构里程碑，才能请求检测/质控资料。
3. 在原件无法解析或信息有争议时只能产出参考候选与用户 Todo，**绝不冒称真实 GIS/现场采样/实验室工作已经完成**。
4. 项目资料、下游任务、Human Todo、成果下载行为与 CI 回归一致。

必要的基础可靠性在这一阶段修补：任务重试不重放旧成功结果；重复事件不创建重复 Todo；若允许修订已接受资料，需对受影响结果作最小必要的失效或重新核查处理。**不为此提前开发一个大型流程引擎。**

**验收**：从空项目到最终文件，人工操作可在一个工作台完整完成；失败状态有明确回退路径；至少一项真实 Codex+Plugin 调用贯穿过程。

### P5 — Codex 版可用发布

开发：
- 简单启动和首次使用体验：检测 Node、Codex CLI 版本、Codex 登录/模型状态、插件状态；提供非技术用户可理解的错误信息。
- Windows/macOS/Linux 安装和运行说明；根据实际上机测试列出**已验证**的平台，不臆测支持情况。
- 持久化项目与附件的备份/恢复说明；本地权限、安全边界、模型/API 费用说明。
- 收敛 UI：**Human TodoList 是主要入口**；Agent 队列、材料路线图、事件记录按需展示；不增加聊天作为项目控制中心。
- 移除或归档 Mastra 原型代码和无关研究入口，减少依赖、维护复杂度与过长 README；保留研究资料作为补充。
- 完成回归测试、README、最小演示案例、版本标记和 Release Note。

**验收**：新用户从干净电脑按 README 安装 → 使用自己已配置的 Codex 运行环境 → 新建项目 → 完成一次涉及插件的工作流 → 查看来源、处理异常、得到成果；无演示占位符冒充真实结果。仓库 CI、跨平台手动验收和安全边界检查均通过。

## 4. 任务优先级与依赖

```text
P0 固定协议与适配层
      │
      ▼
P1 Codex 本地执行真闭环  ◄── 第一关键门槛
      │
      ▼
P2 原生 Skills/Plugins 真闭环 ◄── 第二关键门槛
      │
      ▼
P3 项目模板识别/提取/验证方法
      │
      ▼
P4 真实项目工作流端到端验收
      │
      ▼
P5 打包、文档、测试、Codex Edition 发布
```

**失败时如何处理：**
- P1 如果官方 app-server 无法满足实际任务生命周期/隔离要求，先用 SDK/CLI 的受支持接口验证；若关键问题只能通过修改开源 Codex 内核解决，**才重新评估 fork**。
- P2 若本机缺少文档插件，应先验证插件安装与能力发现机制；不要立即开发解析器。确实没有现成满足要求的工具时，可以先允许手动输入/人工 Todo 完成基本项目，同时将该类能力标明为 unavailable。
- P3 若模板规则无法被结构化表达，再做最小 schema 扩展，而不是预先加入一堆通用 DSL。

## 5. 当下应该开的第一张开发任务

**P1.1 · 本地 Codex app-server 最小调用**

- 编写后台进程管理与 JSON-RPC 客户端；
- 完成 `initialize` → `model/list` → `thread/start` → `turn/start` → `turn/completed`；
- 按本仓库 `hh.task/1` / `hh.result/1` 桥接一次简单任务；
- 将真实进度/失败状态送到工作台，并保存执行 ID；
- CI 使用录制/模拟 app-server 消息，不依赖真实 API Key；真实 Codex 登录环境另行验收。

**在 P1.1 没跑通前，不再开展新的 PDF/DOCX 实验、Octop 适配或项目级功能重构。**

## 6. 暂不启动的项目

- Octop 中国生态适配与国内模型整合；先保留 `ExecutorAdapter` 的抽象边界即可。
- Codex / Octop 双 fork、独立 Agent 内核重写。
- 新的模板搜索、推荐、交易市场、技能市场。
- 自研 PDF/DOCX/OCR/GIS 通用插件、全面的解析器质量竞赛。
- 新建审批中心或额外的人工工作队列。
- 生产级公网、多用户、租户隔离及真正的监管/商业报告签署流程。

## 7. 实施原则

1. **完成可演示的垂直闭环，优先于横向罗列能力。**
2. **真实执行记录与测试证据优先于 UI 上写“已支持”。**
3. **项目业务状态、材料处理方法与 Agent 执行机制严格分离。**
4. **复用 Codex 的本地执行和已有插件生态，不绑定 Codex Cloud。**
5. **Codex 版稳定后才讨论 Octop，中国版不拖慢 V1。**
