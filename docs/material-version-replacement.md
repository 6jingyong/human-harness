# Human Harness · 原件补充、版本替换与下游失效

**2026-11-09 · 本地单机原型。** 保留左右双列 Todo、Agent 分组及汉堡抽屉，不新增文件审批中心，不开发文档语义解析器。

## 用户流程

- 原 Agent 通过模板授权的 `materialRequests` 暂停，左栏产生 Human Todo。用户可以文字回答，也可以在该资料类型允许接收原件时上传文件。
- 文字回答仍被标注为“人工说明，未经独立验证”，不会自动成为已核验文件。上传附件则把问题保持在 `awaiting_review`；必须通过已有来源/版本验收。退回后问题恢复 `pending`，可重新提交。
- 资料管理页可主动替换已接受的原件，提交新版本后在 Human Todo 审核；**提交不等于接受，不立即撤销旧输出**。
- 新版本通过审核才切换 `acceptedArtifactId`。若是 Agent 因补文件暂停，核验完成后才向原 Agent 释放新原件字节和人工说明；开启自动调度时自动继续，暂停自动调度时保持 ready 等待操作。

## 下游最小必要失效

- 根据**项目模板的依赖图**求影响范围：直接消费该材料的 `needsMaterials`、声明可请求该资料的 `requestableMaterialIds` 步骤，以及其通过 `dependsOn`、`when` 条件关联的后继步骤。
- 这些步骤已完成、待审核或失败的状态重新进入依赖检查；若涉及人工决策，原决策重开。无关分支保留其成果与审核状态。
- 历史原件和成果不删除；相关旧 Agent 产物带 `invalidatedAt`，失去当前“已审核可导出”的资格。下载接口仅允许当前已完成步骤的**最新且未失效**成果，避免重做后再下载旧版本。
- 若替换将影响正在执行或等待人工补充的其他任务，材料接受会返回 **409 冲突**，要求先结束/取消相关任务再审核，避免活跃任务依据被中途替换。
- 旧的动态 Human 问答在其所属 Agent 任务因原件替换被失效时保留历史但不再自动注入，避免旧回复混入新版本。

## 技术边界

`RuntimeMaterial.acceptedArtifactId` 精确指向最近通过人工审核的原件；`artifactIds` 保留全部提交版本。旧项目首次替换时从已接受状态的最后一份资料初始化此引用，避免要求迁移全部旧数据。

**没有做**：公网/多用户权限、真实 PDF/DOCX 格式和内容鉴真、逐页事实正确性审查、跨进程锁、Agent 远端主动停止计算、跨项目引用、批量工作流引擎。文件验收仍遵循模板已有的格式/规则并要求人类确认；当前自动检查仅处理协议边界、原件存储和版本关系，不宣称语义质量自动通过。

## 验收方法

- `tests/material-replacement.test.ts`：两个独立 Agent 分支与合流的选择性失效；旧输出不可导出；新版本被实际用于重跑；文件问答先审后恢复；附件退回重传；活跃任务阻止替换。
- `tests/api-scheduler.test.ts`：真实 FormData 上传新版本、Human 补件与核验、409 冲突。
- `tests/browser/workbench.spec.ts`：Chromium 中操作项目资料页的“替换原件”，回到 Human Todo 审核后检查任务重新打开，并保存最新截图。
- Codex 和文档 Skills 的真实执行保持独立验收，Demo/测试文件不代表实际 PDF 内容提取。
